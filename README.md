# kconc · Linux 内核并发检错与可信优化

两个线程各给寄存器设置一位，为什么最后只留下一位？打上补丁后，怎样确认测试又走到了那组交错？kconc 在真实 Linux 内核里记录线程的中间读写，重放出错的路径，再用相应的交错检查修复。它能在 KX022A 和 BMA400 原生驱动上重放三个读者同时处于驱动中的时机，也能在 Ubuntu 测试内核上核对三个线程更新同一个寄存器的顺序。可信优化部分用 BMA400 验证了跳过空转换的正确性和实际收益。

## 团队做了哪些探索

上一版，我们在 KX022A 和 BMA400 上重放了两个线程分别读 X、Y 轴的过程。这次加入读 Z 轴的第三个线程。三个读者最后都能拿到数据，但我们想知道的是，第一笔读取还没开始传输时，另外两个读者有没有机会都进入驱动？我们先让普通软件板自然运行，从记录里找到这个时机，再让软件板重现它。两款驱动都沿用原有的代码和锁，工具逐一核对三个线程的身份、它们进入驱动的时间，以及第一笔请求何时真正开始传输。

第三个线程也让我们看到了浅层搜索容易错过的问题。我们在同一个 RAM 寄存器上给三个线程各分一位，每个线程先占用、再释放，约定最多只能同时占用两位。跑完后寄存器总会回到零。我们于是把每一步的读写都留下来，跑遍这个用例的 90 种顺序。只换两三次线程时，所有路径都符合约定；换到四次，第一次看见三位同时被占用。沿着线程时间线，可以直接找到谁占用了第三个名额。

为了看这套核对办法能不能换一份内核使用，我们保留 openEuler 来宾用户空间，用 Ubuntu 的内核重新编译同一个测试模块。我们让 A 完成一次更新，等 B 和 C 都写完，再唤醒原来的 A。A 读到了 C 留下的 7。把第三步改成提前唤醒 A，它读到的就成了 3。两次最后都得到 6，检查器仍然能从中间读写认出哪一次走错了顺序。

## 回看一次寄存器更新

两个调用者分别要把寄存器中的一个位置为 1。初值是 0，两个操作按任一串行顺序完成后都应读到 3。在演示选取的执行中，两个调用者都读到了旧值，最后只读回 1。打开报告，可以沿着各自的读写事件找到对应的内核源码行，再打开一次实际重执行的记录，与原始路径逐项比较。

工具在 QEMU/KVM 中运行真实 Linux 内核。RAM 测试总线提供可复位的初态。受控调用方分别比较拆开的读改写与 `regmap_update_bits()`，以及不同调用者分用两把锁与共用一把锁。工具先采集两种串行顺序，生成交错候选，执行时核对目标访问与控制交接，再用最终寄存器值或临界区进入、退出事件判定性质。它还可按执行反馈分配尝试预算，缩减输入时通过重执行确认原有违例。

| 正式批次 | 判据与结果 |
| --- | --- |
| 原构建路径重放 | 8 个用例各执行 20 次。**159/160** 次完整匹配关键路径。1 次路径偏离计入分母，8 组均达到预定的每组至少 19 次匹配。 |
| 修复版回归 | 在修复构建上重新采样并定位对应操作，8 个用例各执行 5 次。**40/40** 次命中候选，40 次性质判定有效，违例 0 次。 |

两批分别计数。原构建的逐次重放记录保存完整匹配及偏离分类，修复版的验收记录分别列出正式批次和早期尝试。结论适用于这些构造的调用方、输入和交错。离线演示选取其中一例，附原始执行、一次重执行和该例的五次修复回归。[运行与证据复核](docs/RUNNING.md)

## 在两款驱动上重放读取

每个线程通过 Linux IIO 接口读取一个轴。工具从采样中登记驱动入口和各轴的 regmap 读取特征，之后在同一构建的新启动中核对实际轨迹。

| 核对的路径 | KX022A | BMA400 |
| --- | --- | --- |
| 两次完整读取的先后 | 20 次冷启动，每次各测 X→Y 和 Y→X，两种顺序各匹配 20/20 | 同样各匹配 20/20 |
| 一笔 SPI 请求已提交、尚未传输时，另一线程进入驱动 | X 提交 → Y 进入 → X 开始并完成传输，独立冷启动 20/20 匹配 | Y 提交 → X 进入 → Y 开始并完成传输，独立冷启动 20/20 匹配 |
| X 的 SPI 请求已提交、尚未传输时，Y、Z 都进入驱动 | 三个独立读者，20/20 次冷启动匹配 | 同一规则，20/20 次冷启动匹配 |

各行分别计数。软件 SPI 板控制第一笔请求提交后、开始传输前的准备时间，消息仍在总线上依次完成。三轴用例允许 Y、Z 以任一顺序进入驱动。检查器核对线程、同一笔 SPI 消息及三个轴的数据和返回值。第一笔 X 读取跨过两个后发读者的入口，最后由原来的 X 线程从同一次调用返回。[运行与复核](docs/RUNNING.md#三轴读取重放)

## 三个线程更新寄存器

| 场景 | 从记录中能核对什么 | 实测 |
| --- | --- | --- |
| 完整操作顺序搜索 | 每个线程各置位、清位一次。查看每步执行者、读写值和第一次超出占用上限的位置。 | 90 种合法顺序全部执行，另一次启动重放匹配 90/90。其中 36 条曾同时占用三位。 |
| 更新丢失与互斥违例 | 在私有 RAM regmap 上逐线程核对临界区与实际写入；即使终值仍为 7，也能检出三个临界区重叠。 | 正常与人工错误对照共 8 个案例，每例原路径确认 20/20；对应修复构建每例确认 5/5。 |
| Ubuntu 上的操作交接 | 同一协调者逐次放行内核工作线程，依据调度事件核对 A 的休眠和唤醒，再核对恢复后的读取。 | A→B→A 和 A→B→C→A 各有一条参考，各匹配 20/20 次独立冷启动。同终值的 A→B→A→C 被拒绝。 |

Ubuntu 使用 24.04 LTS 的 `linux 6.8.0-31.31` 源码包和项目测试配置，实测内核为 `6.8.1-kconc-ubuntu`。这里的交接发生在完整 regmap 操作之间，A 再次获准时发起下一次更新。表中三线程性质对照由专用用例控制，传感器读取重叠由软件 SPI 板控制。原 MAccConc 默认锁后端的访存点控制以本项目已验收的双线程用例为限。[运行速查](docs/RUNNING.md) · [构建说明](docs/BUILDING.md)

## BMA400 一次六字节读取能省多少

为了单独看清 regmap 自身的软件开销，我们先用受控 RAM 总线测量专用入口。三轴样本占六字节，一次完整调用包括三笔两字节传输。正常 `-O2` 下，原版平均 **61.20 纳秒**，跳过已知空转换后为 **41.44 纳秒**。一次约 60 纳秒的操作平均省下 **19.76 纳秒**，配对耗时下降 **31.47%**（95% 区间 23.41% 至 40.04%）。三种实现轮换启动，每种对照保留 24 对正式批次。作为对照，我们还测了只缓存函数指针、仍执行空回调的版本。相对同一原版，对照版本的耗时降幅估计为 5.20%（区间跨零），我们跳过已知空回调的版本降幅更大，达到 31.47%。

我们也在 BMA400 原生驱动和软件 SPI 外设上验证了推广后的版本：8 帧数据逐字节一致，空调用从 48 次降到 0 次，开启观察后恢复为 48 次；计入加锁和模拟 SPI 传输，完整读取平均从 **253.47 降至 242.31 纳秒**，省下 11.16 纳秒，配对降幅 4.95%。

### 方法的泛化性

在同一套受控 RAM 总线实验中，我们把起始寄存器从 BMA400 的 `0x04` 移到 KX022A 的 `0x06`。六字节读取、三笔传输和计时方式均相同。换窗口后，每帧仍省去六次空调用，读出的字节一致。KX022A 窗口下每次平均省 **18.54 纳秒**，配对耗时下降 **32.20%**（95% 区间 28.68% 至 35.50%）。这个对照检验了同一条规则在不同寄存器窗口上的复用。

### 工具怎样判断哪些读取可以改

在锁定配置的加速度计驱动目录，工具检查了 44 处批量读取，8 处满足改写条件。对变长读取，工具还要从源码找到接收缓冲区的容量依据。实际分配长度与请求相符的调用可以通过。同一条声明里又改写了缓冲区指针，或寄存器参数的计算带有赋值时，工具保留原调用。[扫描与生成补丁](docs/RUNNING.md)

生成器把局部 Coq 证书与生成的 C 源码绑定。证明依赖本次调用期间对象有效、私有格式字段稳定、缓冲区可写且容量足够。准入对象仍走原有缓存或总线路径，读取成功后才可能跳过转换。传输错误沿原路径返回，释放后重新创建的对象重新选定资格。[局部证明与源码检查](proofs/init-regmap/)

项目也在各自的原模型上复现了 PromisingComp 和 SEQ 的优化算法与定理。上述空转换规则和对应的局部证明由本队编写。[证明工件](proofs/) · [工具与源码版本](configs/optimization/)

## 开始使用

从仓库根目录运行以下命令可查看入口。Python 需要 3.11 或更新版本。

```bash
python3 -B kconc.py --help
python3 -B kconc.py commands
```

已有离线演示材料时，解压后用浏览器打开 `demo/index.html`。要从原始记录重新计算表格并生成页面，使用材料中的 `kit/bundle.json`。演示材料、镜像和完整运行档案单独提供。要运行真实内核，使用 WSL Debian、QEMU/KVM x86_64、openEuler 24.03 LTS SP3 用户空间和锁定的实验内核。[运行说明](docs/RUNNING.md) · [环境与构建](docs/BUILDING.md)
